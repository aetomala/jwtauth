# v1.1.0 Benchmark Report

**Date**: 2026-08-17
**Baseline**: v1.0.1 (tag `v1.0.1`, commit `6a53faf`)
**Candidate**: dev (commit `9f3ee2d`)
**Machine**: Apple M4 Max, darwin/arm64
**Method**: `go test -run='^$' -bench=. -benchmem -count=3 ./pkg/...` on both baseline (via `git worktree`) and candidate — `benchstat v1.0.1.txt v1.1.0.txt`

---

## Verdict: PASS — dramatic Cleanup improvement, one documented soft-gate exception

`RefreshStore.Cleanup`'s expiry-indexed rewrite (#271) delivers the expected large improvement on both backends, with no regression on any other tracked operation's latency. One deterministic allocation-count increase on `Store/Redis` crosses the 15% soft-gate threshold on `B/op`/`allocs/op` (not `sec/op`); it is a direct, anticipated consequence of the new `ZAdd` pipeline command the expiry index requires, and is treated as an accepted tradeoff — see [Store/Redis allocation increase](#storeredis-allocation-increase-soft-gate-exception) below.

## Notable Operations

### Cleanup — the headline improvement (#271)

| Benchmark | v1.0.1 | v1.1.0 | Delta |
|---|---|---|---|
| `Cleanup/N=100/Memory` | 1,025 ns/op | 574.7 ns/op | −44% |
| `Cleanup/N=1,000/Memory` | 6,609 ns/op | 602.6 ns/op | −91% |
| `Cleanup/N=10,000/Memory` | 59,158 ns/op | 536.2 ns/op | −99.1% (~110×) |
| `Cleanup/N=100/Redis` | 2,385.4 µs/op | 49.82 µs/op | −97.9% (~48×) |
| `Cleanup/N=1,000/Redis` | 23,668.5 µs/op | 128.9 µs/op | −99.5% (~184×) |
| `Cleanup/N=10,000/Redis` | 240,390 µs/op | 1,143 µs/op | −99.5% (~210×) |

Both backends move from O(n) — cost scales with total stored tokens — to their new documented complexity (Memory: O(k log n) via a `container/heap` min-heap; Redis: O(log n + k) via a namespace-scoped sorted-set index), where k is the number of expired tokens. At N=10,000 with zero expired tokens, Memory's `Cleanup` allocation count drops from scaling with N to a flat 13 allocs/op regardless of N (unchanged from v1.0.1 — Memory's heap traversal was already allocation-free per entry); Redis's drops from 600,150 allocs/op to a flat 70 allocs/op.

### Store/Redis allocation increase (soft-gate exception)

| Benchmark | Metric | v1.0.1 | v1.1.0 | Delta |
|---|---|---|---|---|
| `Store/Redis` | sec/op | 33.33 µs | 36.33 µs | +9.0% |
| `Store/Redis` | B/op | 5.856 Ki | 6.840 Ki | +16.8% |
| `Store/Redis` | allocs/op | 135 | 159 | +17.8% |
| `Store_WithAudience/Redis` | sec/op | 41.07 µs | 43.52 µs | +6.0% |
| `Store_WithAudience/Redis` | B/op | 7.419 Ki | 7.978 Ki | +7.5% |
| `Store_WithAudience/Redis` | allocs/op | 179 | 203 | +13.4% |
| `Store/Memory` | sec/op | 743.6 ns | 796.5 ns | +7.1% |
| `Store_Memory` | B/op | 1.942 Ki | 2.045 Ki | +5.3% |

`Store`'s new `ZAdd` pipeline command (populating the expiry index — see #271) adds one additional Redis command to the write path, deterministically increasing `Store/Redis`'s allocation count by ~24 allocs (~1KB) per call. `B/op` (+16.8%) and `allocs/op` (+17.8%) cross the 15% soft-gate on this one benchmark; `sec/op` (+9.0%, the latency metric that governs user-facing cost) stays well under it, as does every other Store variant on every metric. This was the anticipated regression risk flagged before running the gate (`Store` gained un-benchmarked hot-path work in both backends during #271) — reviewed and accepted as a deliberate, small-in-absolute-terms tradeoff for O(log n + k) `Cleanup`, not a hard stop.

### Thermal throttling artifact (`pkg/tokens` sec/op geomean)

The initial full-suite run showed `IssueAccessToken_jwtauth`, `Sign_GolangJWT`, `Verify_GolangJWT`, and `ValidateAccessToken_jwtauth` — three duplicate pure-RSA benchmarks positioned at the tail of the ~40-minute `pkg/tokens` run — at roughly 2× their expected cost (e.g. `IssueAccessToken_jwtauth`: 56.86µs → 110.43µs). This is inconsistent with #271, which never touches `pkg/tokens` signing/validation code, and with the primary `IssueAccessToken`/`ValidateAccessToken` benchmarks earlier in the same run, which stayed flat (65.21µs → 63.54µs; 4.27µs → 4.20µs).

An isolated re-run of just the affected benchmarks (`-count=5`, ~46s total instead of ~40 minutes) confirmed no regression: `IssueAccessToken_jwtauth` ~67.4µs, `Sign_GolangJWT` ~59.6µs, `Verify_GolangJWT` ~3.4µs, `ValidateAccessToken_jwtauth` ~4.19µs — all within the expected range matching their non-duplicate counterparts. This is the same class of artifact documented in `doc/benchmarks/v0.7.0-report.md`'s "Baseline measurement note": sustained CPU load from a long sequential `./pkg/...` run (this time both the v1.0.1 baseline and v1.1.0 candidate ran the full suite back to back) produces elevated absolute times for benchmarks late in the `pkg/tokens` package, specifically the raw-crypto and observability-tax variants. The reported `pkg/tokens` sec/op geomean of +20.05% is an artifact of this effect, not a real regression.

## Notes

- All deltas are reported as `~` by benchstat (p ≥ 0.100, n=3) — with only 3 samples, benchstat cannot establish a 95% confidence interval (requires ≥ 6). Deltas above are computed directly from the reported means; treat percentages as directional, consistent with prior reports in this directory.
- `B/op` and `allocs/op` are deterministic per code path in Go's benchmark harness (unlike `sec/op`, which is subject to scheduler/thermal noise) — the Store/Redis allocation increase is a reliable measurement, not noise.
- Raw data files: `v1.0.1.txt` (baseline), `v1.1.0.txt` (candidate) in this directory.
