# v1.1.2 Benchmark Report

**Date**: 2026-09-30
**Baseline**: v1.1.1 (tag `v1.1.1`, commit `dec7a5d`)
**Candidate**: dev (commit `643d202`)
**Machine**: Apple M4 Max, darwin/arm64, macOS 26.6.2, Go 1.26.8, `GOMAXPROCS=16`
**Method**: `go test -run='^$' -bench=. -benchmem -count=1` per package, baseline and candidate
interleaved package by package (keys → storage → tokens) for 3 rounds, each side in its own
`git worktree`, under `caffeinate` — `benchstat v1.1.1.txt v1.1.2.txt`. Figures below are medians
of the 3 samples.

v1.1.1 was released from a private fork and never benchmarked. A second, targeted interleaved run
compares the `v1.1.0` tag against the same candidate on the in-memory store and revocation
benchmarks — see [v1.1.0 → v1.1.2](#v110--v112-the-cost-of-the-v111-security-fix).

---

## Verdict: PASS (v1.1.1 → v1.1.2) — one documented exception carried from v1.1.1

No operation regresses ≥ 15% against v1.1.1 on `sec/op`, `B/op`, or `allocs/op`. The headline is
the in-memory `ListTokens` rewrite (#282): −92% at N=1,000 and −99.4% at N=10,000. Its costs —
`MemoryRefreshStore.Store` +7–8% and `ListTokensForUser` / `ListTokensForAudience` +6–13% on the
in-memory store — sit under the 15% soft gate and are documented below.

Against v1.1.0, in-memory store operations and the Manager's revocation paths regress 16–115%.
The increase entered in v1.1.1 (v1.1.1 → v1.1.2 is flat on every affected row) and is the cost of
the GHSA-hwqw-6hv9-q5v6 fix: every refresh token is now emitted as a `tokenref.Ref` digest. It is
accepted as a justified exception to the 15% rule — see [below](#v110--v112-the-cost-of-the-v111-security-fix)
— and the optimization is tracked in #300.

## Notable Operations (v1.1.1 → v1.1.2)

### `MemoryRefreshStore.ListTokens` — digest keyset pagination (#282)

| Benchmark | v1.1.1 | v1.1.2 | Delta | B/op |
|---|---|---|---|---|
| `ListTokens/N=100/Memory` | 6,315 ns | 4,015 ns | −36% | −11% |
| `ListTokens/N=1000/Memory` | 669,368 ns | 51,916 ns | −92% | −52% |
| `ListTokens/N=10000/Memory` | 79.40 ms | 0.51 ms | −99.4% (~157×) | −92% |

Before #282 every page sorted the full token set to impose a stable order on raw-token cursors.
The store now keeps each token's SHA-256 digest in its record and a digest-sorted index that is
rebuilt only after `Store` adds a token or `Cleanup` removes one; pages are a binary search into
that index. Cursors are hex digests, not tokens (ADR-011, ADR-012).

## v1.1.0 → v1.1.2: the cost of the v1.1.1 security fix

Targeted interleaved run, same session and method, `v1.1.0` tag (`853380d`) vs dev (`643d202`) —
raw data in `v1.1.2-confirm-v1.1.0.txt` / `v1.1.2-confirm-dev.txt`:

| Benchmark | v1.1.0 | v1.1.2 | Delta | allocs/op |
|---|---|---|---|---|
| `Store/Memory` | 806.5 ns | 937.8 ns | +16.3% | 22 → 24 |
| `Retrieve/Memory` | 412.5 ns | 498.3 ns | +20.8% | 14 → 16 |
| `Revoke/Memory` | 1,109 ns | 1,281 ns | +15.5% | 11 → 13 |
| `RevokeAllForUser/N=10/Memory` | 1,881 ns | 3,048 ns | +62.0% | 40 → 60 |
| `RevokeAllForUser/N=100/Memory` | 9,892 ns | 21,299 ns | +115.3% | 310 → 510 |
| `RevokeAllForUser/N=1000/Memory` | 87,650 ns | 172,969 ns | +97.3% | 3,011 → 5,011 |
| `RevokeAllForAudience/N=100/Memory` | 10,601 ns | 22,113 ns | +108.6% | 311 → 511 |
| `RevokeAllForAudience/N=1000/Memory` | 92,187 ns | 181,128 ns | +96.5% | 3,012 → 5,012 |
| `RevokeAllForUserAndAudience/N=1000/Memory` | 109,864 ns | 196,054 ns | +78.5% | 4,014 → 6,014 |
| `RevokeAllUserTokens/N=1000` (Manager) | 89,709 ns | 178,938 ns | +99.5% | 3,021 → 5,021 |
| `RevokeRefreshToken` (Manager) | 1,576 ns | 1,990 ns | +26.3% | 21 → 27 |
| `IntrospectToken` (Manager) | 354.7 ns | 379.4 ns | +7.0% | 26 → 32 |

**Cause.** v1.1.1 (ADR-012) replaced raw refresh tokens in log and span arguments with
`tokenref.Ref(token)` — a SHA-256, a hex encode, and 2 heap allocations, about 90 ns per call.
The arguments are evaluated eagerly, so the cost is paid even when the logger is `NoOpLogger`.
In the in-memory bulk-revocation loops the call sits in a per-token `Debug` line under the write
lock, so the allocation delta is exactly +2 per token revoked. `Store/Memory` additionally carries
#282's per-token SHA-256.

**Why it is accepted for v1.1.2.** The 15% rule allows a justified exception. This one is the
cost of closing a credential leak (GHSA-hwqw-6hv9-q5v6), it shipped in v1.1.1 and v1.1.2 does not
add to it, and it lands on `MemoryRefreshStore`, which is documented for testing. On
`RedisRefreshStore` the same ~90 ns per token is small against a round trip — about 0.09 ms added
to a 3.8 ms revocation of 1,000 tokens on in-process miniredis, less against real network RTT —
and no Redis row regresses measurably.

**Follow-up.** #300 (v1.2.0): cut `tokenref.Ref` to at most one allocation, derive refs in
`MemoryRefreshStore` from the digest its records already hold, and stop computing a ref per token
for bulk-loop Debug lines.

The full-suite v1.1.0 raw file (`v1.1.0.txt`, 2026-08-17) is not used for this comparison: its
`pkg/tokens` run was affected by thermal throttling (see `v1.1.0-report.md`) and it was captured
on an older Go and macOS.

## Reading the Token Manager Numbers

The issuance, validation, and introspection benchmarks use `b.RunParallel` across 16 goroutines,
so their ns/op is wall time divided by total operations — aggregate throughput on 16 cores, not
the latency of one call. `RefreshAccessToken` must stop the timer to issue a fresh token pair per
iteration, so it runs serially and reports single-call latency: ~719 µs, almost all of it one
RSA-2048 signature (703 µs measured serially on this machine). Its apparent 12× gap to
`IssueAccessToken` (~62 µs) is the difference between the two measurement modes, not extra work.
`doc/PERFORMANCE.md` now labels which tables are throughput and which are latency.
